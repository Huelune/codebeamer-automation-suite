# GUI 사용 가이드

## 목적

이 문서는 현재 GUI의 실제 사용 흐름과 구현 범위를 정리합니다.
GUI는 최상위 앱 셸에서 작업 영역을 전환하고, `배치 작업`에서는 CLI 업로드 파이프라인을 재사용해 비개발자도 설정, 검증, 업로드를 단계적으로 진행할 수 있도록 구성합니다.

## 현재 구현 범위

현재 GUI는 아래 기능을 실제로 연결합니다.

- 최상위 앱 셸
  - `트래커 작업공간`, `배치 작업`, `실행 기록`, `설정` 전환
  - 앱 시작 시 `트래커 작업공간` 표시
  - `배치 작업` 안에 기존 9단계 create/update/upsert 마법사 보존
  - `케피코`, `이글루` 테마와 테스트 모드 표시 유지
  - API·백그라운드 작업 중 전체 입력을 차단하는 회전형 로딩 오버레이
- 설정 저장과 불러오기
  - 최상위 전용 설정 센터와 6개 설정 영역
  - 이름이 있는 다중 연결 profile과 활성 profile 하나
  - 로컬 암호화, OS 자격증명 저장소, 미저장 방식 중 profile별 선택
  - 명시적 검증·저장·적용과 미저장 이탈 확인
  - credential 제외 가져오기 / 내보내기와 기존 설정 migration
  - 개발자 도구, 세션 진단 로그, API 모니터 사용 여부와 느린 요청 기준
  - 현재 연결 프로필(또는 테스트 모드)·프로젝트·트래커 범위의 이름 있는 전체 업로드 설정 저장 / 불러오기 / 이름 변경 / 기본 지정 / 삭제
- 온라인 / 테스트 모드
  - 온라인 모드에서 Codebeamer 연결
  - 테스트 모드에서 offline schema / 조회 데이터 snapshot 사용
  - 테스트 모드에서는 실제 업로드 차단, Dry Run만 허용
- 트래커 조회 서비스 기반
  - 프로젝트·트래커, 최상위·직접 하위 아이템과 ID 상세 조회 정규화
  - 간편·상세 조건·CbQL에서 현재 tracker ID 범위 강제
  - 계층 서버 페이지 전체 수집과 검색 `page`, `pageSize`, `total` 보존
  - builtin/custom field, 부모·자식, 원본 JSON 민감값 마스킹
  - 두 개 tracker를 포함한 익명 테스트 fixture
- 트래커 작업공간
  - 프로젝트·트래커 선택과 테스트 모드 자동 조회
  - 최상위와 각 노드의 직접 하위를 모두 이어서 표시하는 전체 스크롤 확장형 트리
  - 노드별 하위 결과의 화면 세션 캐시
  - 선택 tracker에만 범위를 고정한 ID/요약·상태·담당자 검색
  - tracker 검색과 분리된 전역 아이템 ID 바로 열기와 조상 경로 표시
  - 선택 아이템 설명, 필드와 마스킹된 원본 JSON 상세 조회
  - 명시적 Wiki 설명·필드 렌더링과 원문 전환, TableField 행·열 전용 보기
  - 백그라운드 요청 token으로 오래된 응답 무시
  - 선택 tracker schema 기반 최상위 또는 선택 아이템 하위 단건 생성
  - 필수 필드 자동 포함, 선택 필드 명시적 포함과 생성 직후 트리·상세 전환
  - schema 기반 선택 필드 부분 수정과 version 충돌 확인
  - 일반 필드 저장과 분리된 Status 필드 변경
  - 아이템 ID 재입력이 필요한 삭제 확인
- 실행 기록
  - 단건 생성·필드 수정·상태 전환·삭제의 성공·실패 결과 저장
  - 배치 작업의 모드·Dry Run·성공·실패·미해결 건수와 소요 시간 요약 저장
  - 작업·결과 필터, ID·아이템·프로젝트·트래커·요약 검색과 선택 상세
  - 최근 500건 로컬 영속화, 민감 키 마스킹과 확인 후 기록 비우기
- API 모니터
  - 별도 최대화 가능 창과 최근 최대 500개 HTTP 시도 메모리 버퍼
  - 요청 종류, method, 정규화 경로, status, 종단 간 지연, 결과와 시도 번호 표시
  - 전체·진행 중·성공률·실패·평균·P50·P95·최대·최근 1분·429·재시도·느린 요청 통계
  - 요청/응답 본문, header, query 값, host, 실제 ID와 원본 오류 문자열 미수집
- 프로젝트 / 트래커 선택
  - 온라인 조회
  - 테스트 모드 자동 채움
- 파일 단계
  - 여러 Excel 파일 동시 선택
  - 대표 파일 미리보기 선택
  - 파일 선택 직후 대표 파일의 시트 이름만 조회
  - `선택 시트 미리보기`에서 헤더와 제한된 행만 조회
  - `전체 데이터 불러오기`에서만 모든 파일의 raw dataframe 로드
  - 파일 경로·크기·수정 시각과 옵션 signature가 같을 때 raw dataframe 캐시 재사용
- 상단 데이터 단계
  - 파일별 루트 parent item 생성 여부 선택
  - 파일명 또는 정규식 group 값을 필드 source로 사용
  - 지원 필드는 고정값도 입력 가능
  - 파일명 정규식 미리보기 제공
- 매핑 단계
  - `id`, `parent`, 내부 생성 컬럼 숨김
  - 체크박스와 콤보박스 기반 필드 매핑
  - 필드별 공통 기본값 지정
  - `TrackerItemChoiceField` 의 ID 추출 정규식 입력 (query 조회는 비활성화)
- 검증 단계
  - 차단 이슈와 안내 이슈 분리
  - 대표 파일 검증 결과 표시
  - 선택 파일 수와 전체 예상 업로드 건수 표시
- 업로드 단계
  - Dry Run / continue on error
  - 총 건수, 현재 항목, 성공 / 실패 / 재시도 수 표시
  - 항목별 시작 / 완료 / 소요 시간과 로그 표시
  - 실패 응답 JSON 표시
- 결과 단계
  - 성공 / 실패 / 미해결 탭 표시
  - 내부 생성 컬럼 숨김

## 빠른 사용 순서

### 온라인 모드

1. 앱 셸에서 `설정 > 연결`을 선택하고 연결 profile을 추가합니다.
2. Base URL, Username, Password와 비밀번호 저장 방식을 지정합니다.
3. `연결 테스트`가 성공하면 `저장`, `적용`을 순서대로 누릅니다.
4. `배치 작업`에서 작업 모드, Header Row, Summary Column, Sheet Name을 확인합니다.
5. 프로젝트 화면에서 프로젝트와 트래커를 불러옵니다.
6. 파일 화면에서 Excel 파일을 하나 이상 선택하고 시트를 정한 뒤 `선택 시트 미리보기`, `전체 데이터 불러오기`를 순서대로 실행합니다.
7. 필요하면 상단 데이터 화면에서 파일별 루트 parent item 규칙을 설정합니다.
8. 매핑 화면에서 업로드 대상 컬럼, 기본값, tracker item 처리 방식을 정합니다.
9. 검증 결과를 확인하고 업로드 화면에서 Dry Run 또는 실제 업로드를 실행합니다.

### 테스트 모드

1. 앱 셸에서 `설정 > 테스트 모드`를 선택합니다.
2. `테스트 모드 사용`을 켜고 schema와 조회 데이터 snapshot 경로를 지정합니다.
3. `Snapshot 검증`, `저장`, `적용`을 순서대로 누릅니다.
4. `배치 작업`의 프로젝트 화면으로 이동하면 테스트 프로젝트와 트래커가 자동으로 채워집니다.
5. 이후 흐름은 온라인 모드와 같지만 실제 업로드는 허용되지 않고 Dry Run만 가능합니다.

샘플 데이터는 [data/gui-offline-sample/README.md](../data/gui-offline-sample/README.md)를 참고합니다.

## 화면별 설명

### 앱 셸

- 좌측에서 `트래커 작업공간`, `배치 작업`, `실행 기록`, `설정`을 전환합니다.
- 좌측 메뉴 상단의 화살표로 메뉴를 접거나 펼칩니다. 접힌 상태에서도 `조회`, `배치`, `기록`, `설정` 라벨과 전체 이름 툴팁을 유지합니다.
- 메뉴 접힘 상태는 창 크기와 함께 저장되어 다음 실행 시 복원됩니다. 설정 화면 내부의 6개 카테고리 메뉴는 접지 않습니다.
- 상단에는 현재 온라인 설정, 테스트 모드 또는 연결 미설정 상태를 표시합니다.
- `배치 작업`을 선택하면 기존 9단계 마법사가 같은 창 안에서 열립니다.
- `트래커 작업공간`은 프로젝트·트래커 선택, 계층·검색·ID 직접 접근, 상세 조회와 별도 수정 탭을 실제 서비스에 연결합니다.
- `실행 기록`은 단건 쓰기와 배치 작업의 최종 결과를 통합하고, 배치 행별 실시간 로그는 기존 배치 화면에 유지합니다.

### 트래커 작업공간

1. 프로젝트와 트래커 목록을 새로고침하거나 테스트 모드 snapshot에서 자동으로 불러옵니다.
2. 트래커를 선택하면 서버 페이지를 끝까지 수집해 `계층` 탭에 최상위 아이템 전체를 하나의 스크롤 목록으로 표시합니다.
3. 펼침 표시가 있는 행을 열면 해당 아이템의 직접 하위 전체를 조회합니다. 같은 화면 세션에서 다시 펼칠 때는 캐시를 사용합니다.
4. 행을 선택하면 오른쪽에서 설명, builtin/custom field와 민감값이 마스킹된 원본 JSON을 확인합니다.
   Wiki로 명시된 값만 rich text로 표시하며 원문으로 전환할 수 있습니다.
   상세 ID 배지를 누르면 `#`을 제외한 숫자 ID만 클립보드에 복사합니다.
5. `트래커 검색`은 현재 선택한 tracker 안에서만 동작합니다. 간편 검색은 ID/요약·상태·담당자를 사용합니다. 상세 조건 검색은 별도 큰 창에서 편집하며, 한 묶음 안의 조건은 모두 만족하고 여러 묶음 중 하나만 만족해도 검색되며 조건별 제외 방식도 지원합니다. 맨 위 `조회 기준`은 계층 탭과 같은 값이며, Baseline을 고르면 그 시점 안에서 검색하고 결과는 그 시점 상세로 읽기 전용으로 엽니다. 이때 선택과 일괄 수정 줄은 숨기고, 조회 기준이 바뀌면 다른 시점 결과를 비웁니다.
6. 상단 `ID 바로 열기`는 tracker 검색과 별도입니다. 아이템 소속 프로젝트·트래커를 확인한 뒤 조상 경로와 상세로 바로 전환합니다.
7. `새 아이템`에서는 최상위 또는 현재 선택 아이템의 하위 위치를 고르고, 필수 필드와 명시적으로 포함한 선택 필드만 입력합니다.
8. 생성된 아이템은 계층 트리에 선택된 상태로 추가되고 오른쪽 상세가 열립니다.
9. `수정` 탭에서는 변경할 필드만 체크하고 현재 값과 새 값을 비교한 뒤 부분 저장합니다.
10. 상태는 별도 선택기로 전환하며, 삭제는 아이템 ID를 다시 입력해야 실행됩니다.
11. 검색 결과는 현재 페이지 또는 조건에 맞는 전체 결과를 선택할 수 있습니다. 선택은 페이지 이동 후에도 유지되고 개별 제외가 가능합니다. 프로젝트 이동·ID 바로 열기·즐겨찾기로 트래커가 바뀌면 검색 결과와 선택을 비우고, 다른 트래커의 검색 선택으로는 일괄 수정하지 않습니다.
12. 일괄 수정은 일반 필드·상태·TableField를 같은 값으로 대체하거나 명시적으로 비웁니다. 대상 수에는 상한을 두지 않고 기억된 청크 크기로 나눠 `PUT /v3/items/fields`를 호출합니다.
13. `청크 내 원자적 처리`는 기본으로 켜며 실패 시 직접 실패와 함께 롤백된 청크 대상을 구분합니다. 실행 기록에서 실패 청크 또는 실패 ID를 재시도할 때 실제 값은 다시 입력합니다. 진행 창은 작업이 끝날 때까지 닫히지 않고 Esc·창 닫기는 `남은 청크 중단` 요청으로 받으며, 실행 중에는 일괄 수정을 다시 시작하지 않습니다. 청크 요청이 응답 없이 실패하면 거기서 멈추고 앞 청크 결과와 멈춘 청크부터의 재시도 대상을 기록합니다. 재시도는 실행 기록을 만든 것과 같은 서버·계정으로 연결했을 때만 허용합니다.
14. `Baseline 비교`는 기준과 비교 대상을 선택한 뒤 사용자가 `전체 비교 실행` 경고를 확인한 경우에만 트래커 전체를 조회합니다. 전체 결과는 결과 유형·ID/이름·단일 변경 필드를 AND 조건으로 필터링하며, 이 과정에서는 캐시만 사용합니다. 신규·삭제 아이템도 선택 필드가 존재하면 포함하고 상세는 선택 아이템의 모든 필드를 계속 표시합니다. Excel은 현재 표시된 아이템과 선택 필드만 2단 병합 헤더로 내보내며 필드 선택 창의 전체 선택·전체 해제는 검색으로 숨겨진 필드까지 적용합니다. 한 셀의 안전 한도를 넘는 값은 비교표의 미리보기 링크와 `긴 값 전체보기` 시트의 기준·비교 분할 행으로 보존합니다.
15. 기본 `계층` 탭은 조회 기준으로 현재 상태 또는 Baseline을 선택합니다. Baseline은 명시적 조회 시 전체 query 결과로 계층을 완성하고 동일 시점 상세만 읽기 전용으로 표시하며, 현재 계층 API와 모든 쓰기 기능을 사용하지 않습니다. 조회가 완료된 Baseline 계층은 캐시와 schema를 재사용해 선택 필드와 함께 Excel로 내보내며 추가 item query나 단건 조회를 실행하지 않습니다.
16. `계층 Excel 내보내기`는 현재 트래커 전체 `items` query와 최상위 목록을 페이지 끝까지 수집하고 parent/children 참조로 계층을 재구성합니다. ID·Summary·계층 단계·상위 ID는 고정 열이며 일반 필드는 기본 선택, TableField는 기본 해제합니다. 계층 정보가 불완전하면 단건 조회로 우회하지 않고 저장을 중단합니다.

동작 원칙:

- 프로젝트, 트래커, 최상위, 하위, 검색, 상세와 ID 경로 요청은 GUI thread 밖에서 실행합니다.
- API 응답을 기다리는 동안 앱 전체에 spinner와 현재 작업 메시지를 표시하고 메뉴 이동, 재조회와 추가 쓰기 입력을 차단합니다.
- 연속되거나 중첩된 요청은 모든 작업이 끝난 뒤에만 로딩 오버레이를 닫습니다. 성공·실패 모두 같은 해제 경로를 사용합니다.
- 선택이나 설정이 바뀐 뒤 늦게 도착한 이전 응답은 request token과 현재 컨텍스트를 비교해 무시합니다.
- 계층은 서버 pagination을 내부적으로만 사용하고 모든 페이지를 합쳐 표시합니다. 이전/다음 버튼은 두지 않습니다.
- tracker 검색은 서버가 pagination 요청을 실제로 적용한 경우에만 이전/다음 버튼을 활성화합니다.
- 읽기 화면은 서버 원본 dict를 직접 해석하지 않고 조회 서비스의 불변 모델만 사용합니다.
- Wiki 렌더링 여부는 `descriptionFormat`, field/column `type`과 `valueModel`로만 판단하며 문자열 패턴으로 추측하지 않습니다.
- 필드 수정은 전체 item `PUT` 대신 `PUT /v3/items/{itemId}/fields`를 사용하며 저장 직전에 version을 다시 확인합니다.
- 단건 생성은 `POST /v3/trackers/{trackerId}/items`를 사용하며 하위 생성에만 `parentItemId`를 전달합니다.
- 상태는 생성 payload에 넣지 않고 서버 기본값으로 만듭니다. 현재 작업공간은 workflow transition이 아닌 Status 필드 변경만 제공합니다.
- 테스트 모드에서는 편집 widget을 확인할 수 있지만 생성, 저장, Status 필드 변경과 삭제를 실행할 수 없습니다.
- 테스트 모드에서는 일괄 수정도 실행할 수 없습니다.

### 실행 기록

1. 화면을 열면 앱 설정 폴더의 최근 실행 결과를 최신 순으로 불러옵니다.
2. 작업 종류와 결과 상태를 선택하거나 ID·아이템·프로젝트·트래커·요약으로 검색합니다.
3. 표에서 기록을 선택하면 작업 위치, 대상, 결과 요약과 안전한 세부 정보를 아래에 표시합니다.
4. 일괄 수정의 실패 대상이 있는 기록은 값 재입력 후 재시도할 수 있습니다.
5. `기록 비우기`는 확인 대화상자를 거쳐 저장된 로컬 기록 전체를 비웁니다.

기록 대상은 트래커 작업공간의 단건 생성·수정·상태 전환·삭제·일괄 수정, Baseline Excel 내보내기와 배치 작업의 최종 결과입니다. 조회와 검색은
서버 상태를 바꾸지 않으므로 기록하지 않습니다. 배치는 입력 파일명을 저장하지 않고 작업 모드, Dry Run 여부,
파일 수, 성공·실패·미해결 건수와 소요 시간만 저장합니다. token, password, authorization, cookie, session 계열
세부 값은 저장 전에 마스킹합니다. 자세한 계약은 [통합 실행 기록](./activity-history.md)을 참고합니다.

### 1. 전용 설정 화면

주요 항목:

- `연결`: profile 이름, Base URL, Username, Password, 비밀번호 저장 방식, 활성 profile
- `화면`: `케피코` / `이글루` 테마
- `네트워크·저장소`: Retry Delay, Max Retries, Output Directory
- `테스트 모드`: 전역 토글, Schema Snapshot, 조회 데이터 Snapshot
- `개발자`: 개발자 도구 열기, API 모니터 사용 여부와 느린 요청 기준
- `데이터 관리`: credential 제외 설정 가져오기 / 내보내기

동작 원칙:

- 변경은 자동 저장하지 않으며 다른 작업 영역으로 이동할 때 `저장`, `변경 취소`, `돌아가기`를 선택합니다.
- 연결 profile 또는 테스트 snapshot은 현재 값의 검증 signature가 성공 결과와 일치해야 적용할 수 있습니다.
- 저장과 적용은 분리되며, 저장한 설정만 현재 작업공간과 배치 작업에 명시적으로 적용합니다.
- 로컬 암호화 파일이 기본 비밀번호 저장 방식입니다. `keyring` backend가 있는 환경에서는 OS 자격증명 저장소로 전환할 수 있습니다.
- OS 저장소를 사용할 수 없으면 선택을 비활성화하고 기존 로컬 암호화 또는 미저장 방식을 유지합니다.
- 저장소 전환은 대상 credential 기록과 재조회 검증이 성공한 뒤 기존 저장소를 정리하며, 실패하면 원래 설정과 credential을 복원합니다.
- 테스트 모드는 이 화면에서만 켜고 끄며, 적용된 경우 앱 셸에 `테스트 모드` 배지를 표시합니다.
- 개발자 도구는 진단 로그와 API 모니터를 탭으로 제공합니다. API 모니터를 켜고 적용하면 API 탭을 열며, 창을 닫아도 수집은 계속됩니다. 진단 로그는 별도 설정 없이 세션 메모리에만 보관하고 안전한 ZIP으로 명시적으로 내보낼 수 있습니다. 자세한 계약은 [개발자 도구와 진단 패키지](./developer-tools.md)와 [Codebeamer API 모니터](./api-monitor.md)를 참고합니다.
- 기존 `gui_settings.json`과 version 1 workflow preset은 원본을 보존한 채 새 전역 설정으로 migration합니다.

### 2. 배치 설정 화면

- 전역 설정 중 작업 모드, Header Row, Summary Column, Sheet Name만 전체 업로드 설정에 포함합니다.
- 연결·테마·재시도·출력 위치·테스트 모드는 전용 설정 화면에서 관리합니다.
- 현재 연결 프로필(또는 테스트 모드)·프로젝트·트래커에 이름 있는 전체 업로드 설정을 여러 개 저장하고 불러오기·덮어쓰기·이름 변경·기본 지정·삭제할 수 있습니다.
- 각 범위에는 설정이 하나 이상이면 기본 설정이 정확히 하나 있으며, 기본 설정을 삭제하면 남은 설정 하나가 기본으로 승계됩니다.
- 기본 설정은 현재 범위의 목록에서 처음 선택되는 항목이며 자동으로 파일을 읽거나 설정을 적용하지는 않습니다.
- 각 설정은 파일 옵션, 상단 데이터, 매핑, 기본값, tracker item 설정을 함께 다루며 다른 연결이나 트래커에서는 목록과 기본 선택에서 제외됩니다.
- 이름 있는 설정 파일에는 비밀 없는 연결 scope만 저장하고 URL·사용자명·비밀번호·전역 출력 경로·offline snapshot 경로·최근 Excel 파일 경로는 저장하지 않습니다.
- 기존 단일 전체 설정 파일은 이름 있는 목록에 자동 편입하지 않으며 사용자가 호환 항목을 선택한 경우에만 불러옵니다.
- 기존 단일 version 3 파일은 호환 불러오기용으로 유지하고, 이름 있는 collection version 2는 위의 더 제한적인 저장 계약을 사용합니다.

### 4. 파일 화면

주요 항목:

- Excel 파일
- 미리보기 파일
- 시트
- 헤더 행
- Summary 컬럼

중요한 동작:

- 파일을 고르면 대표 파일의 시트 이름만 먼저 읽고 전체 데이터는 읽지 않습니다.
- `선택 시트 미리보기`는 헤더와 제한된 행만 읽습니다.
- Summary 컬럼은 미리보기 전에는 비활성화하고, 미리보기에서 확인한 실제 헤더만 선택 후보로 제공합니다.
- `전체 데이터 불러오기`를 눌러야 선택된 모든 파일을 읽고 다음 단계가 활성화됩니다.
- 여러 파일을 고르면 대표 파일을 바꿔가며 미리보기를 확인할 수 있습니다.
- 저장된 파일 설정을 다시 불러온 뒤에도 제한 행 미리보기와 전체 데이터 로드를 다시 실행해야 다음 단계로 갈 수 있습니다.
- 전체 설정을 불러오면 이전 매핑·검증·업로드 결과를 무효화하고 파일 단계로 돌아가므로, 과거 raw data에 새 매핑이 잘못 적용되지 않습니다.
- 전체 로드는 파일별 경로·크기·수정 시각과 시트·헤더 행·Summary 옵션 signature가 같으면 캐시를 재사용하고, 원본 파일이 바뀌면 다시 읽습니다.

### 5. 상단 데이터 화면

의미:

- 각 Excel 파일의 모든 업로드 row를 하나의 루트 parent item 아래에 넣고 싶을 때 사용하는 단계입니다.
- 옵션을 끄면 루트 parent item을 만들지 않고 기존 업로드 흐름만 사용합니다.

지원 기능:

- 파일명(확장자 제외) 또는 전체 파일명을 정규식 대상으로 선택
- 정규식 전체 match 또는 group 값을 source로 선택
- 필드별 `소스 값`(파일명·정규식 결과) 또는 `고정값` 선택
- 파일명 파싱 미리보기

현재 기본 동작:

- schema 의 `name` builtin 에 대응하는 루트 item 제목 필드는 기본적으로 파일명(확장자 제외)을 사용합니다.
- 제목 필드 외 나머지 필드는 고정값 또는 schema 지원 방식에 따라 따로 지정할 수 있습니다.

- 오류 시 중단하거나 사용자가 취소하면 이미 완료된 결과를 유지하고, 준비를 마쳤지만 실행하지 않은 READY 행은 미해결 결과와 세션 재시도 대상으로 보존합니다.
- 파일 준비 전에 취소되어 payload가 없는 파일은 자동 재시도 대상으로 가장하지 않으며, 사용자가 흐름을 다시 실행해야 합니다.
- 서버 처리가 끝난 뒤 로컬 상태 파일 저장이 실패해도 서버 결과와 세션 재시도 정보는 버리지 않고 실시간 로그에 경고합니다.

### 9. 결과 화면

탭:

- 성공
- 실패
- 미해결

지원 동작:

- 실패 보고서는 파일명·Excel 행·작업·대상 ID·HTTP 상태·안전한 오류 요약만 Excel로
  내보내고 payload, 원본 응답, 절대 경로와 인증값은 제외합니다.
- 결과 표와 실패 보고서의 Excel 행은 `Excel 4행`, 여러 줄이 합쳐진 아이템은 `Excel 4-6행`처럼
  원본 파일의 실제 행입니다. 파일별 최상단 폴더 행은 원본 행이 없어 비워 둡니다.
- `실패 항목 재시도`는 현재 앱 세션에서 실패·미해결인 행만 다시 실행합니다.
  이미 성공한 행과 상위 항목은 재생성하지 않으며 create/update/upsert를 지원합니다.
- 재시도 자체를 취소하거나 오류 시 중단해도 아직 실행하지 않은 대상은 현재 앱 세션의 후속 재시도 context에 유지합니다.
- 파일 준비, 매핑 또는 payload 생성 단계 자체가 실패한 항목은 자동 재시도하지 않고
  검증 단계에서 원인을 수정하도록 안내합니다.
- 재시도 cache는 앱 종료 또는 새 업로드 시작 시 폐기됩니다.

표시 원칙:

- `_row_id`, `parent_row_id`, `payload_json`, `__lookup_*` 같은 내부 컬럼은 숨깁니다.
- 실패 응답 JSON 이 있으면 첫 실패 응답을 하단 뷰어에 표시합니다.

## UX 관련 변경 사항

- 긴 페이지는 내부 스크롤로 처리합니다.
- 단건 생성 창과 TableField 편집 창은 전체 화면을 지원하고, 수정 탭은 입력 상태를 유지한 채 별도 창으로 분리할 수 있습니다.
- 창 높이는 화면 높이의 88%를 넘지 않도록 제한합니다.
- 기본 창 크기는 `1160x780`, 최소 크기는 `860x620`입니다.
- 앱 셸의 좌측 탐색 영역은 필요할 때 68px 너비로 접을 수 있고, 실제 작업 데이터 영역이 가로와 세로로 우선 확장됩니다.
- 입력 검증 오류는 수정 위치 가까이에 표시하고, 트래커 조회·쓰기·Baseline Excel 저장·배치 파일 작업 실패는 화면 상태와 오류 다이얼로그를 함께 표시합니다.
- Qt 슬롯 또는 Python thread의 처리되지 않은 예외는 전역 예외 처리기가 콘솔 traceback을 보존하면서 사용자에게 안전한 오류 알림을 표시합니다. 같은 오류의 연속 알림은 짧은 시간 동안 중복 억제합니다.
- 백그라운드 worker 생성·시작 실패도 로딩 상태와 진행 창을 정리한 뒤 기존 실패 경로로 전달합니다.

## 현재 제한 사항

- 테스트 모드에서는 실제 Codebeamer 업로드를 지원하지 않습니다.
- `TableField`는 schema에서 확인한 일반 값 열만 수정합니다. 참조 열과 `ReferredTestStep` 행은 읽기 전용이며, 새 아이템 생성에서는 아직 지원하지 않습니다.
- 유형이 불명확한 mixed member/reference field는 작업공간에서 아직 수정할 수 없습니다.
- 통합 `실행 기록`은 최종 결과 요약만 보관하며, 배치 행별 실시간 로그와 원본 오류 응답은 `배치 작업`에서 확인합니다.
- 현재 실행 환경에 사용 가능한 `keyring` backend가 없으면 OS 자격증명 저장 방식은 비활성화됩니다.
- 배치 create 후 `Status` transition 후처리와 작업공간의 실제 workflow transition은 아직 구현하지 않았습니다. 현재 작업공간 동작은 Status 필드 부분 갱신입니다.
- `TrackerItemChoiceField` 의 이름·summary query lookup은 대량 검증의 API 호출을 줄이기 위해 비활성화되어 있습니다.
- offline snapshot 에 사용자 / 그룹 데이터가 없으면 관련 lookup 은 실패하도록 유지합니다. 작업공간 조회는 별도 `조회 데이터 Snapshot`이 있어야 활성화할 수 있습니다.
- 결과 화면의 상세 상호작용은 아직 최소 구성입니다.

## 권장 테스트 시나리오

1. offline sample 두 파일을 함께 선택해 다중 파일 preview / validation / Dry Run 흐름을 확인합니다.
2. 상단 데이터 옵션을 켜고 파일명 정규식 미리보기가 예상대로 나오는지 확인합니다.

4. 기본값이 비어 있는 행에서 올바르게 fallback 되는지 확인합니다.
5. 실패 응답 JSON 과 항목별 진행 기록이 업로드 화면에 남는지 확인합니다.
