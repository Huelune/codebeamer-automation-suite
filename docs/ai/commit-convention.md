# 커밋 규칙

Git 커밋을 만들거나 제안할 때 따르는 규칙입니다. 사람과 에이전트 모두에게 적용됩니다.
[Simulink Test Automation Toolkit의 커밋 규칙](https://github.com/Huelune/Simulink-Test-Automation-Toolkit/blob/main/docs/ai/commit-convention.md)을
바탕으로 이 저장소의 한글 메시지 규칙과 문서 갱신 규칙에 맞췄습니다.

## 가장 중요한 기준

**커밋 로그만 읽어도 프로젝트가 어떤 이유로 어떻게 바뀌었는지 알 수 있어야 합니다.**

커밋 수를 줄이는 것보다 다음을 우선합니다.

- 변경 목적의 명확성
- 독립적인 롤백 가능성
- 변경 이력 추적 가능성

## 기본 원칙

**커밋 하나에는 논리적 변경 하나만 담습니다.**

- 파일 개수가 아니라 변경 목적을 기준으로 나눕니다.
- 서로 따로 되돌릴 수 있는 변경은 별도 커밋으로 나눕니다.
- 기능 추가, 관련 없는 리팩터링, 문서 수정을 한 커밋에 섞지 않습니다.

메시지는 **Conventional Commits 형식**을 따르고, `type`과 `scope` 외의 내용은 **한글로** 씁니다.

```text
<type>: <summary>
```

scope는 필요할 때만 붙입니다.

```text
<type>(<scope>): <summary>
```

`summary`에는 바꾼 파일이 아니라 **무엇을 왜 바꿨는지**가 드러나게 씁니다.

`summary`는 `~ 추가`, `~ 분리`, `~ 방지`처럼 **명사형으로 끝냅니다.** `~한다`, `~했다`, `~함` 같은
문장형으로 끝내지 않습니다. 끝말보다 앞의 대상과 조건이 구체적이어야 합니다.

| | 예 |
| --- | --- |
| 좋음 | `fix: 값 칸 클릭 시 해당 행의 수정·포함 자동 선택` |
| 좋음 | `feat: 트래커 선택 시 새 아이템 필수 필드 미리 표시` |
| 좋음 | `refactor: 검색·일괄 수정 탭을 TrackerSearchPanel로 분리` |
| 좋음 | `test: 모듈 정리 시 자동완성 팝업 이중 삭제 방지` |
| 나쁨 | `fix: 코드 수정` |
| 나쁨 | `chore: 파일 변경` |
| 나쁨 | `feat: 기능 추가` |
| 나쁨 | `fix: 버그 수정` |
| 나쁨 | `feat: 트래커 선택 시 필수 필드를 미리 보여 준다` (문장형) |

## Type

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 새 기능 또는 기존 기능의 의미 있는 확장 |
| `fix` | 실제 오류나 잘못된 동작 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선. 타입 주석 정리도 여기에 넣습니다 |
| `test` | 테스트 코드, 테스트 케이스, 검증 로직 변경 |
| `docs` | 문서만 변경 |
| `chore` | 설정, 환경, 의존성, 기타 유지보수 |
| `build` | 패키징, 배포 산출물 생성 방식 변경 |
| `ci` | GitHub Actions 등 CI 설정 변경 |
| `perf` | 성능 개선 |
| `style` | 포맷팅, lint 지적 정리처럼 동작에 영향이 없는 변경 |
| `revert` | 기존 커밋 되돌리기 |

`chore`를 의미 없이 쓰지 않습니다. 기능이나 버그 수정이면 `feat`, `fix`를 먼저 씁니다.
예전 이력의 `types:`, `quality:`, `lint:` 같은 표 밖의 type은 새로 쓰지 않습니다. 타입 주석 정리는
`refactor`, lint 지적 정리는 `style` 또는 `refactor`로 씁니다.

## Scope

scope는 **분명히 도움이 될 때만** 씁니다.

```text
fix(upload): 같은 행 재업로드 시 기존 아이템 조회 실패 수정
feat(wiki): 설명의 첨부 이미지 본문 자리 표시
refactor(settings): 연결 프로필 검증을 저장 흐름에서 분리
```

GUI가 주력 경로라 `gui` scope는 대부분 정보가 되지 않습니다. 구조가 자주 바뀌므로 폴더 경로나
지나치게 세부적인 모듈 이름을 scope로 고정하지 않습니다.

## 커밋 분리 기준

다음은 가능하면 별도 커밋으로 나눕니다.

- 새 기능 구현
- 기존 버그 수정
- 대규모 리팩터링
- 테스트 추가·수정
- 설정 또는 의존성 변경
- 생성 파일이나 결과물 변경

단, 어떤 기능을 위해 반드시 함께 바뀌어야 하고 따로 떼면 의미가 없는 변경은 한 커밋에 둡니다.
새 기능이나 수정을 지키는 테스트는 그 커밋에 함께 넣고, 이미 있는 코드에 테스트만 더할 때는
`test` 커밋으로 나눕니다.

**커밋 수를 억지로 늘리지 않습니다.** 작은 변경 여러 개가 하나의 목적을 이루면 하나로 묶습니다.

### 변경을 설명하는 문서는 해당 커밋에 넣습니다

`docs/feature-status.md`, README, 관련 가이드처럼 그 변경을 설명하는 문서는 변경을 만든 커밋에
함께 넣습니다. 별도 `docs` 커밋으로 빼면 기능 커밋만 되돌렸을 때 없는 기능이 문서에 남습니다.

같은 이유로, 변경과 떨어지면 이력이 어긋나는 다른 파일(`pyproject.toml`의 규칙, 샘플 데이터 등)도
함께 넣습니다.

### 리팩터링이 함께 일어날 때

기능 변경과 리팩터링이 같이 생기면 가능하면 순서대로 나눕니다.

```text
refactor: ...
feat: ...
```

```text
refactor: ...
fix: ...
```

기능 구현에 필요한 작은 구조 변경은 억지로 나누지 않습니다. 구조 개선이 중심인 리팩터링은
`AGENTS.md`의 브랜치 규칙대로 기능 병합 뒤 별도 브랜치와 PR로 나눕니다.

## 메시지 작성 방식

- 한 줄 summary는 짧고 분명하게 씁니다.
- 구현 방법보다 결과와 의도를 먼저 씁니다.
- `코드 수정`, `파일 변경`, `업데이트`처럼 무엇을 바꿨는지 없는 summary는 쓰지 않습니다.
- 같은 내용의 커밋 메시지를 반복하지 않습니다.
- `WIP`, `temp`, `test123`, `final`, `final2` 같은 메시지는 쓰지 않습니다.
- 코드를 확인하지 않고 커밋 메시지를 짐작해서 쓰지 않습니다.

### 본문

summary만으로 변경 이유가 부족할 때만 본문을 씁니다. 본문도 `~한다` 문장 대신 짧은 개조식으로
씁니다.

```text
fix(upload): 그룹 폴더가 다른 동명 아이템 구분

- 아이템 이름만으로 조회해 다른 그룹 폴더의 같은 이름 아이템끼리 덮어쓰던 문제
- 그룹 폴더 경로를 포함한 식별자로 조회하도록 변경
```

본문에는 다음 중 필요한 것만 담습니다.

- 왜 바꿨는지
- 기존 방식의 문제
- 중요한 설계 결정
- 호환성 또는 영향 범위

코드를 그대로 풀어 쓰는 긴 본문은 쓰지 않습니다.

## Breaking Change

기존 사용 방법, 설정 파일 형식, 출력 구조가 깨지면 반드시 표시합니다.

```text
feat!: 업로드 결과 Excel 열 순서 변경
```

필요하면 본문 아래에 덧붙입니다. `BREAKING CHANGE:` 표시는 도구가 읽으므로 영어 그대로 둡니다.

```text
BREAKING CHANGE: 결과 Excel 첫 열이 아이템 ID로 바뀌어 기존 매크로 수정 필요
```

## 에이전트 작업 시 추가 규칙

코드 수정이 끝나도 바로 커밋하지 않고 먼저 변경 내용을 분석합니다.

1. `git diff`와 변경 파일을 확인합니다.
2. 변경을 논리적인 단위로 나눕니다.
3. 커밋마다 담을 파일과 변경 영역을 정합니다.
4. 목적이 다른 변경이 섞였으면 나눕니다.
5. 각 커밋 메시지를 위 규칙대로 씁니다.
6. 테스트가 실패하거나 미완성 코드가 있으면 커밋하지 않고 먼저 사용자에게 알립니다.

사용자가 명시적으로 요청하지 않으면 기존 이력을 rewrite 하거나 squash, force push 하지 않습니다.

여러 커밋이 필요하면 커밋하기 전에 계획을 먼저 보여 줍니다.

```text
1. refactor: 상세 영역을 TrackerDetailPanel로 분리
2. feat: 상세 개요 탭 설명 칸의 창 크기 연동 확장
3. test: 개요 탭 레이아웃 회귀 테스트 추가
```

그다음 각 변경을 해당 커밋에만 넣습니다. 검증을 통과했다면 `AGENTS.md`의 작업 절차대로 승인을
기다리지 않고 이어서 커밋합니다.
